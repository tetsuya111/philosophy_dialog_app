## 背景・課題

本アプリの中核体験は「4人単位でランダムにマッチングされたユーザー同士が、Jitsi Meet のグループビデオ通話上で哲学対話を行う」ことである（[.kiro/steering/product.md](../../steering/product.md)）。しかし現状は、この体験を構成する部品が個別に存在するだけで、1本の導線としてつながっていない（[philosophy-dialog-app](../philosophy-dialog-app/requirements.md) の「既知の課題」も参照）。

- **マッチングと通話が連携していない**: `backend/matching/` は待機列（`WaitingQueue`）が4人に達すると `Room` を作成するが、`Room` は通話ルーム名を持たず、フロントエンドの通話画面（`frontend/app/meeting.tsx`）とも接続されていない。マッチングされた4人を同じ通話ルームに導く手段がない。
- **Home画面の「対話をはじめる」ボタンが機能していない**: `frontend/app/(tabs)/index.tsx` の「対話をはじめる」は見た目だけのボタンで、押しても何も起きない。現状、通話に入れるのは「一人で対話を開始する」（端末内で生成したルーム名で単独入室）のみである。
- **マッチング処理の不備**: 待機キャンセルが元の待機エントリを削除しない、状態変更を `GET` で行う、マッチング成立時に状態が「未参加（`NONE`）」に戻り「マッチング済み」を表現できない、`post_save` シグナルに依存したグルーピングで同時実行時の排他が考慮されていない。
- **フロントエンドにログイン・API 呼び出しの仕組みがない**: マッチング API は JWT 認証必須だが、フロントエンドにはログイン画面もバックエンド API の呼び出し処理も存在しない。本スペックではログイン画面は作らず、ログインなしで利用できる形で実装する（ストーリー6）。

本機能は、Home画面の「対話をはじめる」ボタン1つで待機列に並び、4人が揃ったら自動的に同じ通話ルームへ入室できるようにすることで、「知らない人と偶然に哲学対話をする」という本アプリの中核体験を初めて成立させる。

参考として、同コンセプトを別プロジェクト（community_sns）向けに定義した `random-call` スペック（`/home/tetsuya/projects/community_sns/.kiro/specs/random-call/requirements.md`）の要件構成を踏襲した。ただし本プロジェクトの実情に合わせ、以下の点を変えている。

- **対象クライアント**: 参考スペックは Web（Next.js）のみだが、本プロジェクトは Expo による Android ネイティブ版（`Meeting.tsx`）と Web 版（`Meeting.web.tsx`）の通話画面が既に動作しているため、両方を対象とする
- **通話画面**: 参考スペックでは別スペック（video-call）で定義したが、本プロジェクトでは既存の通話画面（`app/meeting.tsx` + `components/Meeting*.tsx`）を流用するため、流用にあたって必要な変更のみを本スペックで定義する
- **通話後のグループチャット**: 本プロジェクトには DM・チャット機能が存在しないため、Non-Goals とする

## ゴール

- ユーザーがログインせずに、Home画面の「対話をはじめる」ボタンを押すだけで待機列に参加できる
- 待機列に4人集まった時点で、先に並んだ4人が自動的に1つのグループとしてマッチングされる
- マッチングされた4人全員が、既存の通話画面を使ってそのグループ専用の Jitsi 通話ルームに参加できる（Android ネイティブ版・Web 版の双方）
- 通話ルームには発行から30分の有効時間があり、満了時に通話は終了する
- 待機中のユーザーは、マッチング前であればいつでも待機を取りやめられる
- 5分以内にマッチングされなかった待機中のユーザーは自動的に待機列から外れ、再度参加できる

## Non-Goals（やらないこと）

- ログイン・ユーザー登録画面、および本機能の利用とアカウント（`CustomUser`）の紐付け。一旦ログインなしで実装し、ログインは必要になった時点で別スペックとする
- マッチング条件の指定（「今日の問い」・テーマ・年齢等によるフィルタリング）。マッチングは完全にランダム（待機列の先着順）とする
- マッチングしたグループへの「今日の問い」の提示（Home画面の「今日の問い」カードの表示も変更しない）
- 4人以外のグループサイズの選択。人数は固定とする
- 通話後のグループチャット・DM 機能（参考スペックのストーリー6・7に相当）。本プロジェクトにはチャット基盤がないため、必要になった時点で別スペックとする
- 「ルーム」タブ（`app/(tabs)/rooms.tsx`、現状ダミーデータ）とマッチングしたグループとの連携、過去の通話履歴の閲覧
- 通話の録画・文字起こし・要約、Jitsi SDK の標準機能を超えるモデレーション機能（強制退出・ミュート等）
- Jitsi サーバーの自前ホスティング（[self-host-jitsi-server](../self-host-jitsi-server/requirements.md) で検討中）。本スペックでは既存の通話画面と同じく公開インスタンス `meet.jit.si` を使い、そのレート制限・障害への対策は行わない
- マッチング成立や通話開始のプッシュ通知。アプリを開いている間の画面上の状態表示のみを対象とする
- ブロック・通報等のユーザー保護機能との連携、同じ相手との再マッチング防止
- iOS 版での動作確認（現状 Android と Web のみで動作確認している。コード上は共通のため動作を妨げはしない）
- 「一人で対話を開始する」ボタンの挙動変更（現状のまま残す）

## 成功指標 (Success Metrics)

| 指標 | 目標値 | 計測方法 |
| --- | --- | --- |
| マッチング成立後、グループ全員が同じ通話ルーム識別子を取得できた割合（誤ったルーム・取得失敗が発生しない） | 100% | バックエンドのアクセスログ集計 |
| マッチング成立後、実際に通話ルームに入室したメンバーの割合 | 要決定（初期リリース後に実測して基準値を決める） | 入室記録の集計 |
| 待機列参加からマッチング成立までの待ち時間の中央値 | 要決定（利用者数に依存） | 待機列エントリの作成日時とマッチング成立日時の差分 |
| 待機列参加のうち、タイムアウトで離脱した割合 | 要決定（初期リリース後に実測し、タイムアウト時間の妥当性判断に使う） | 待機列エントリの離脱理由（マッチング成立 / 取りやめ / タイムアウト）の集計 |
| 待機列・グループの不整合（同一ユーザーの二重所属、4人以外のグループ）の発生件数 | 0件 | グループ・待機列テーブルの突合 |

## 対象ユーザー

- アプリの利用者全員（ログイン不要）
- Android ネイティブアプリ、または Web ブラウザ（Expo Web）から利用するユーザー

## ユーザーストーリーと受け入れ基準

書き方の詳細（INVEST原則・EARS記法・曖昧な表現を避ける方法）は [docs/requirements-best-practices.md](../../../docs/requirements-best-practices.md) を参照。

### ストーリー1: ランダムコールへの参加（待機列への参加）

As a ユーザー, I want Home画面の「対話をはじめる」ボタンを押して待機列に並ぶ, so that 知らない相手と哲学対話をする機会を得られる。

**受け入れ基準:**

1. WHILE ユーザーの状態が「未参加」である THE SYSTEM SHALL Home画面（`app/(tabs)/index.tsx`）の既存の「対話をはじめる」ボタンを押下可能な状態で表示する
2. WHEN ユーザーが「対話をはじめる」ボタンを押したとき THE SYSTEM SHALL そのユーザーを待機列の末尾に追加し、ユーザーの状態を「待機中」にする
3. IF 利用者識別子（ストーリー6）を伴わない待機列への参加要求を受けた場合 THEN THE SYSTEM SHALL 要求を拒否する
4. IF 既に「待機中」のユーザーが再度待機列への参加を要求した場合 THEN THE SYSTEM SHALL 待機列に重複して追加せず、現在の状態（待機中）を返す
5. IF 既に「マッチング済み」または「通話中」のユーザーが待機列への参加を要求した場合 THEN THE SYSTEM SHALL 要求を拒否し、現在の状態を返す
6. WHILE ユーザーが「待機中」である THE SYSTEM SHALL Home画面上に待機中であることを表示する
7. IF 待機列への参加要求が通信エラー等で失敗した場合 THEN THE SYSTEM SHALL 失敗したことを表示し、ユーザーの状態表示を「未参加」のままにする
8. THE SYSTEM SHALL 既存の「一人で対話を開始する」ボタンの挙動（待機列を介さず単独で通話画面に入る）を変更しない

### ストーリー2: 待機の取りやめとタイムアウト

As a 待機中のユーザー, I want 待機を取りやめる, so that 予定が変わったときにマッチングされずに済む。

**受け入れ基準:**

1. WHILE ユーザーが「待機中」である THE SYSTEM SHALL Home画面に「待機をやめる」操作を表示する
2. WHEN 「待機中」のユーザーが待機の取りやめを要求したとき THE SYSTEM SHALL そのユーザー自身の待機列エントリを削除し、ユーザーの状態を「未参加」に戻す
3. IF 「待機中」でないユーザーが待機の取りやめを要求した場合 THEN THE SYSTEM SHALL 要求を拒否し、現在の状態を返す
4. IF 待機の取りやめ要求とマッチング成立が同時に発生した場合 THEN THE SYSTEM SHALL いずれか一方のみを有効にし、「グループに含まれているのに待機列にも残っている」「待機列から消えたのにグループに含まれていない」という不整合を生じさせない
5. IF ユーザーが待機列に参加してからタイムアウト時間（5分）が経過してもマッチングが成立しなかった場合 THEN THE SYSTEM SHALL そのユーザーの待機列エントリを削除し、ユーザーの状態を「未参加」に戻す
6. WHEN タイムアウトにより待機列から外れたとき THE SYSTEM SHALL Home画面上に「相手が見つからなかった」ことを表示し、再度「対話をはじめる」を押せる状態にする
7. IF タイムアウトとマッチング成立が同時に発生した場合 THEN THE SYSTEM SHALL 受け入れ基準4と同様にいずれか一方のみを有効にし、不整合を生じさせない
8. WHILE ユーザーが「待機中」である THE SYSTEM SHALL タイムアウトまでの残り時間を秒単位で表示する

### ストーリー3: 4人のランダムマッチング

As a 待機中のユーザー, I want 待機列に4人集まったら自動的にグループを組んでほしい, so that 自分で相手を探さなくても対話を始められる。

**受け入れ基準:**

1. THE SYSTEM SHALL 待機列を先入れ先出し（FIFO）のキューとして管理し、参加した順序を保持する
2. WHILE 待機列の人数が4人未満である THE SYSTEM SHALL グループを作成しない
3. WHEN 待機列の人数が4人に達したとき THE SYSTEM SHALL 待機列の先頭から4人を取り出して1つのグループを作成する
4. WHEN グループが作成されたとき THE SYSTEM SHALL 該当4人の待機列エントリを削除し、各ユーザーの状態を「マッチング済み」にする
5. WHEN グループが作成されたとき THE SYSTEM SHALL そのグループに対して一意で推測困難な通話ルーム識別子を発行する
6. THE SYSTEM SHALL 1人のユーザーが同時に複数の未終了グループに属さないことを保証する
7. IF 複数のユーザーがほぼ同時に待機列に参加した場合 THEN THE SYSTEM SHALL 同一ユーザーが複数のグループに含まれたり、4人未満または5人以上のグループが作成されたりしないことを保証する
8. WHILE ユーザーが「待機中」で Home画面を表示している THE SYSTEM SHALL マッチング成立から5秒以内に、そのユーザーの画面にマッチング成立を反映する

### ストーリー4: グループ専用の通話ルームへの入室

As a マッチング済みのユーザー, I want 既存の通話画面から自分のグループ専用の通話ルームに入室する, so that マッチングされた相手と実際に対話できる。

**受け入れ基準:**

1. WHEN マッチング成立が画面に反映されたとき THE SYSTEM SHALL Home画面に「対話に参加」操作を表示する
2. WHEN ユーザーが「対話に参加」を押したとき THE SYSTEM SHALL 既存の通話画面（`app/meeting.tsx`）に、バックエンドから取得したグループの通話ルーム識別子をルーム名として渡して遷移する
3. WHEN 通話画面がグループの通話ルーム識別子で開かれたとき THE SYSTEM SHALL Android ネイティブ版では既存の `components/Meeting.tsx`、Web 版では既存の `components/Meeting.web.tsx` を用いて、「一人で対話を開始する」と同じ Jitsi サーバーの当該ルームに入室させる
4. WHEN グループに属するユーザーが通話ルーム識別子を要求したとき THE SYSTEM SHALL そのユーザーが属する未終了グループの通話ルーム識別子を返す
5. IF どのグループにも属していないユーザーが通話ルーム識別子を要求した場合 THEN THE SYSTEM SHALL 拒否する
6. WHEN ユーザーが通話画面でグループの通話ルームへの入室を開始したとき THE SYSTEM SHALL そのユーザーの状態を「通話中」にする
7. WHILE ユーザーが「マッチング済み」または「通話中」である THE SYSTEM SHALL Home画面に通話ルームの有効時間の残りを分単位で表示する
8. IF ユーザーが「マッチング済み」または「通話中」の状態でアプリを再起動した、または通話画面から Home画面に戻った場合 THEN THE SYSTEM SHALL 有効時間内であれば「対話に参加」操作を再度表示し、同じ通話ルームに再入室できるようにする
9. THE SYSTEM SHALL Jitsi 上の表示名をアプリから設定せず、既存の「一人で対話を開始する」と同じく Jitsi の標準の挙動に任せる（ログインなしのためアプリ上のユーザー名が存在しない）

### ストーリー5: 通話の終了と有効時間の満了

As a 通話中のユーザー, I want 通話を途中で終了できる一方で、有効時間が来たら全員の通話が自動的に終わってほしい, so that 対話の区切りを自分で決めつつ、際限なく続かない安心感を持って参加できる。

**受け入れ基準:**

1. THE SYSTEM SHALL 通話ルームの有効時間を発行から30分とし、この値は後から変更しやすいようバックエンドの1箇所の定数（設定値）で管理する
2. WHEN ユーザーが通話画面で通話終了操作を行ったとき（既存の `onReadyToClose` / Web 版の相当イベント） THE SYSTEM SHALL 既存どおり直前の画面に戻り、バックエンドにそのユーザーの通話終了を記録し、状態を「未参加」に戻す
3. WHEN ユーザーの状態が「未参加」に戻ったとき THE SYSTEM SHALL 再び「対話をはじめる」を押せる状態にする
4. IF 他の参加者が有効時間の満了前に退室した場合 THEN THE SYSTEM SHALL 残っている参加者のグループを「終了」状態にせず、通話を継続させる
5. WHEN 通話ルーム発行から有効時間が経過したとき THE SYSTEM SHALL そのグループを「終了」状態にし、以後そのグループの通話ルーム識別子の取得を拒否する
6. WHEN 有効時間が満了したとき THE SYSTEM SHALL そのグループに属し「マッチング済み」または「通話中」のままのユーザーの状態を「未参加」に戻す
7. WHILE ユーザーがグループの通話ルームで通話している THE SYSTEM SHALL 有効時間の満了時に通話画面側で通話を終了し、Home画面に戻す
8. WHEN グループの全メンバーの通話終了が有効時間の満了前に記録されたとき THE SYSTEM SHALL そのグループを「終了」状態にし、以後そのグループの通話ルーム識別子の取得を拒否する
9. IF ユーザーが通話終了を記録できないまま通話画面を離れた場合（アプリの強制終了・通信断など） THEN THE SYSTEM SHALL 遅くとも有効時間の満了時にそのユーザーの状態を「未参加」に戻す

### ストーリー6: ログインなしでの利用者の識別

As a ユーザー, I want ログインせずにランダムコールを使う, so that アカウント登録の手間なくすぐに対話を始められる。

**受け入れ基準:**

1. WHEN フロントエンドが初めて本機能の API を呼び出すとき THE SYSTEM SHALL 推測困難な利用者識別子を発行し、その端末（Web 版ではそのブラウザ）に保存する
2. THE SYSTEM SHALL 本機能の全 API 呼び出しに利用者識別子を付与し、バックエンドは利用者識別子ごとに待機列・グループ・ユーザーの状態を管理する
3. WHEN アプリを再起動した、または Web 版でページを再読み込みしたとき THE SYSTEM SHALL 保存済みの利用者識別子を再利用し、同じユーザーとして扱う
4. THE SYSTEM SHALL 本機能の API をログイン（JWT 認証）なしで呼び出せるようにする。既存の `accounts` の API の認証要件は変更しない
5. THE SYSTEM SHALL フロントエンドが接続するバックエンドの URL を、ソースコードに埋め込まず環境ごとに設定できるようにする
6. WHILE Web 版からバックエンド API を呼び出す THE SYSTEM SHALL ブラウザのクロスオリジン制約により呼び出しが拒否されないようにする

端末（ブラウザ）の保存データを消した場合は別のユーザーとして扱われる。その時点で「待機中」「マッチング済み」「通話中」だった元の利用者は、タイムアウトまたは有効時間の満了で「未参加」に戻る（ストーリー2-5、5-9）。

## 非機能要件

| 種別 | 要件 |
| --- | --- |
| 性能 | 待機列への参加・取りやめ・状態取得・通話ルーム識別子取得・通話終了記録の各APIは、通常時1秒以内に応答する。マッチング成立は、4人目が待機列に加わってから5秒以内にグループ作成まで完了する |
| セキュリティ | 本機能の API はログインなしで利用できるが、利用者識別子を必須とする。利用者識別子・通話ルーム識別子はいずれも推測困難な値とし、通話ルーム識別子は当該グループのメンバーの利用者識別子に対してのみ返す。他人の利用者識別子を知らない限り、その人の待機を取りやめたり状態を変えたりできないようにする。待機列・ユーザー状態を変更する操作は `GET` 以外のメソッドで提供し、プリフェッチ・再読み込み等で状態が変わらないようにする |
| 整合性 | 待機列への参加・取りやめ・タイムアウトによる離脱・グループ作成・有効時間満了は、同時実行下でも不整合（同一ユーザーの二重所属、4人以外のグループ、待機列とグループの両方に存在する状態）を生じさせない |
| プライバシー | 通話の音声・映像は自前インフラを経由せず、公開 Jitsi サーバー（`meet.jit.si`）を経由する。マッチング相手には、Jitsi 上でユーザー自身が入力した表示名（未入力なら Jitsi の既定の表示）以外の情報を開示しない |
| 互換性 | Android ネイティブ版と Web 版で同じ受け入れ基準を満たす。既存の「一人で対話を開始する」フローの動作を損なわない |
| アクセシビリティ | 現時点で特別な要件なし |

## 依存関係

- ログインなしで実装するため、`backend/accounts/`（ユーザー認証・JWT）には依存しない。ただし既存の `WaitingQueue` / `Room` / `matching_status` は `CustomUser` に紐付いているため、その扱いは design.md で決定する（「制約・前提条件」参照）
- 既存の `backend/matching/`（`WaitingQueue` / `Room` / `UserMatchingStatus`）を拡張して実装する
- 既存のフロントエンド通話画面（`app/meeting.tsx`、`components/Meeting.tsx`、`components/Meeting.web.tsx`）と Home画面（`app/(tabs)/index.tsx`）を流用する（「制約・前提条件」参照）
- 外部サービス: Jitsi Meet 公開インスタンス（`meet.jit.si`）。[self-host-jitsi-server](../self-host-jitsi-server/requirements.md) で自前ホスティングに移行した場合も、通話ルーム識別子の受け渡し方は変わらない想定
- Web 版の API 呼び出しには、バックエンドへの CORS 設定の追加が必要（現状 `django-cors-headers` 未導入）

## 制約・前提条件

- **フロントエンドの既存処理を流用する。** 具体的には次の通り。
  - Home画面の既存の「対話をはじめる」ボタン（現状は押しても何もしない）を、本機能の待機列参加ボタンとして使う。画面レイアウト・「今日の問い」カード・「一人で対話を開始する」ボタンは維持する
  - 通話画面は `app/meeting.tsx`（`room` パラメータを受け取り `Meeting` を描画する）をそのまま使い、ルーム名としてグループの通話ルーム識別子を渡す。「一人で対話を開始する」が `router.push({ pathname: '/meeting', params: { room } })` で遷移しているのと同じ方式とする
  - Jitsi の組み込み（ネイティブ版 `@jitsi/react-native-sdk` の `JitsiMeeting`、Web 版の `external_api.js`）、サーバー URL、通話終了時に `router.back()` で戻る挙動は既存実装を使う。追加が必要なのは、通話終了・満了をバックエンドへ記録／反映する処理と表示名の設定のみ
  - Android ネイティブ版のビルド・Jitsi 周りの既知の回避策（`.env` の `EXPO_ROUTER_DISABLE_RN_NAVIGATION_CHECK` 等）は変更しない
- **バックエンドは既存の `matching` アプリの構成（待機列テーブル・グループテーブル・ユーザーの状態フィールド・join/cancel API）を基本的に尊重する。** ただし [philosophy-dialog-app](../philosophy-dialog-app/requirements.md) の「既知の課題」に挙がっている不備（キャンセルが元の待機エントリを削除しない、状態変更を `GET` で行う、成立時に状態を `NONE` に戻す、`post_save` シグナル依存で排他がない）は再現せず改める。既存 API のパス・メソッドを変更してよい（現状フロントエンドから呼ばれていないため互換性の考慮は不要）
- ユーザーの状態は「未参加」「待機中」「マッチング済み」「通話中」の4つとする。既存の `UserMatchingStatus`（`NONE` / `WATING` / `JOINED`）をどう拡張・対応付けるかは design.md で決定する
- 待機列の人数（4人）は既存の `WAITING_LIMIT_N` と同様に定数で管理し、UI 上での選択は提供しない
- 待機列のタイムアウトは5分とし、有効時間と同じく1箇所の定数で管理する。起点は待機列への参加時刻とする。タイムアウト・有効時間満了の検知方式（状態取得時に判定する、定期処理で判定する等）は design.md で決定する
- マッチング成立・満了の画面反映（ストーリー3-8、5-7）の実現方式（ポーリング・WebSocket 等）は design.md で決定する。現状のバックエンドはステートレスな HTTP API のみで構成されている
- **ログインなしで実装する（2026-09-19 の回答）。** 利用者は端末（ブラウザ）ごとの利用者識別子で見分ける（ストーリー6）。既存の `WaitingQueue`・`Room` は `CustomUser` への外部キー、ユーザーの状態は `CustomUser.matching_status` で持っているため、「利用者識別子ごとにゲスト用の `CustomUser` を自動作成する」「`matching` 側に利用者識別子を直接持たせる」などの方式は design.md で決定する。将来ログインを導入する際にアカウントへ移行しやすい方式を優先する
- 参考: 既存のログインAPI（`POST /api/auth/login/`）はアクセストークンを httpOnly Cookie に設定し、`shared/middleware.py` の `AuthorizationHeaderMiddleware` がそれを `Authorization: JWT <token>` ヘッダーに詰め替える。ブラウザでは使えるが、Android ネイティブ版で httpOnly Cookie を扱う方法は未検討であり、ログインを導入する別スペックで扱う（2026-09-19 の実装時に、当初「Cookie だけでは認証が通らない」と記載していた誤りを訂正）
- フロントエンドの起動・実機／エミュレータでの動作確認はユーザーが手動で行う（[CLAUDE.md](../../../CLAUDE.md)）。4人でのマッチングの動作確認には4アカウント・4クライアント（Web ブラウザの複数ウィンドウ等を含む）が必要になるため、手順は `manuals/` にマニュアルとして作成する

## 未解決事項 (Open Questions)

2026-09-19 の回答により、以下はすべて解消した。

1. **ログイン・ユーザー登録画面をどこで作るか** => 一旦ログインなしで実装する。ストーリー6を「ログインなしでの利用者の識別」に改め、ログイン画面・アカウントとの紐付けは Non-Goals に移した。これに伴い、ストーリー1の未ログイン時の基準を削除し、Jitsi の表示名はアプリから設定しないことにした（ストーリー4-9）
2. **通話ルームの有効時間** => 30分で確定（ストーリー5-1）
3. **待機列のタイムアウト** => 5分に変更（ストーリー2-5、「制約・前提条件」）
4. **「今日の問い」との関係** => 不要。グループへの提示は行わない（Non-Goals）
5. **マッチング成立後に入室しないメンバー** => 有効時間の満了まではグループを終了しない仕様で問題なし（ストーリー5-8）

現時点で未解決事項はなし。

## 用語集

| 用語 | 定義 |
| --- | --- |
| ランダムコール | 待機列に並んだユーザーを先着順に4人ずつ組み合わせて行うグループビデオ通話（哲学対話）。本スペックで定義する機能全体の名称 |
| 待機列 | ランダムコールへの参加を要求したユーザーが、マッチングされるまで並ぶ先入れ先出し（FIFO）のキュー。既存の `WaitingQueue` |
| マッチング（成立） | 待機列の先頭4人を取り出して1つのグループを作成すること |
| グループ | マッチングで組み合わされた4人のユーザーの集合。既存の `Room` に相当し、1つの通話ルーム識別子と有効時間を持つ |
| 通話ルーム（通話ルーム識別子） | Jitsi 上のルーム名で識別される通話の単位。グループ1つに対して1つ発行され、推測困難な値とする。通話画面（`app/meeting.tsx`）の `room` パラメータとして渡される |
| 有効時間 | 通話ルームの発行から通話が自動的に終了するまでの時間。30分とし、定数で管理する |
| タイムアウト | 待機列に参加してからマッチングされずに自動的に待機列から外れるまでの時間。5分とし、定数で管理する |
| 利用者識別子 | ログインなしで利用者を見分けるための、端末（Web 版ではブラウザ）ごとに発行・保存される推測困難な値。本機能の API 呼び出しに付与する |
| ユーザーの状態 | ランダムコールに関するユーザーの状態。「未参加」「待機中」「マッチング済み」「通話中」の4つを取る。既存の `UserMatchingStatus` を拡張して表現する |
| 通話画面 | 既存の `app/meeting.tsx` と、そこから描画される `components/Meeting.tsx`（Android ネイティブ版、`@jitsi/react-native-sdk`）/ `components/Meeting.web.tsx`（Web 版、Jitsi の `external_api.js`） |
| 一人で対話を開始する | Home画面の既存ボタン。マッチングを介さず `solo-<timestamp>-<random>` 形式のルーム名で単独入室する。本機能では変更しない |
